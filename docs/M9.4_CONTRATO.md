# M9.4 — Contrato Operacional da Bateria de Eval

**Status:** ativo
**Criado em:** 2026-09-30
**Substitui:** definição nominal "A–H" (não recuperável)
**Documento irmão:** docs/M9.3_DECISAO.md

---

## 1. Motivo deste contrato

O `MILESTONES.md` registra M9.4 como "Bateria A–H executada" e marca o
item como **BLOQUEADO: definição operacional não recuperável**.

Em `docs/M9.3_DECISAO.md` §Fora de escopo, o mesmo bloqueio é
confirmado.

Ou seja: a *intenção histórica* de "Bateria A–H" se perdeu. O que
sobreviveu foi a implementação concreta em
`backend/src/caixaclaro/eval/runner.py`, com verificações numeradas
`Gate 0..8`, e a suíte `backend/tests/test_eval_gates.py`.

Este contrato resolve a ambiguidade **sem reescrever a história**:
ele define M9.4 operacionalmente a partir do que pode ser observado
e verificado hoje.

---

## 2. O que NÃO é afirmado aqui

Este contrato **não afirma** e **não pressupõe**:

1. Que "A" corresponda ao Gate 0, "B" ao Gate 1, e assim por diante.
2. Que existam exatamente oito itens na bateria. O runner tem nove
   verificações (Gate 0 a Gate 8).
3. Que a ordem `Gate 0 → Gate 8` seja a ordem originalmente pensada
   para a bateria.
4. Que a bateria "A–H" tenha sido, em algum momento, implementada
   integralmente sob esse nome.
5. Que os thresholds atuais (`B_MIN`, `C_MIN`, `C_MAX`, `DATASET_MIN`)
   sejam os valores originalmente acordados — eles são os valores
   **observáveis no código atual**.

Qualquer tentativa de fazer A–H "casar" com os gates é reconstrução
especulativa. Este contrato a rejeita explicitamente.

### 3.2 Verificações do runner

Sem afirmar correspondência com A–H, os gates observáveis são:

| Gate | Verificação |
|------|-------------|
| 0    | Schema do envelope (JSON Schema) |
| 1    | `taxonomia_version` do dataset == `TAXONOMIA_ESPERADA` |
| 2    | `TAXONOMIA_VERSION` do código == `TAXONOMIA_ESPERADA` |
| 3    | `|A| >= DATASET_MIN` |
| 4    | Métrica A == 0 |
| 5    | Métrica B >= `B_MIN` |
| 6    | Métrica C dentro de [`C_MIN`, `C_MAX`] |
| 7    | Sem abstenção em `easy` / `medium` |
| 8    | Métrica D == 0 |

Os nomes e valores exatos das constantes devem ser lidos em
`runner.py` — este contrato não os duplica para não criar
divergência.

### 3.3 Evidência existente

- Cada gate tem pelo menos um teste dedicado em
  `test_eval_gates.py` (positivo e/ou negativo).
- O endpoint tem cobertura para 404, 200 e 500 em
  `test_eval_api.py`.
- O golden dataset tem 34 casos, acima do mínimo verificável.

## 4. Definição operacional de M9.4

**M9.4 está concluído quando, e somente quando, todas as etapas
abaixo forem verdadeiras e evidenciáveis:**

1. O golden dataset (`tests/golden/dataset_v1.json`) é carregado
   sem erro de schema.
2. `avaliar_com_gates` executa **todos** os gates `Gate 0..8` sobre
   o dataset completo.
3. O runner produz um resultado global (envelope com métricas e
   `ok`/`falha`).
4. O resultado é gravado via `--publicar CAMINHO`. Para o
   endpoint expô-lo, `CAMINHO` deve coincidir com
   `EVAL_ULTIMA_EXECUCAO_PATH`.
5. A execução acontece no CI a cada push relevante (não apenas
   localmente).
6. O endpoint `/api/v1/eval/ultima-execucao` retorna o snapshot
   publicado com `200`.
7. Existe artefato ou log de CI que comprove (5) e (6).

Enquanto qualquer uma dessas etapas não for demonstrável, M9.4
permanece **aberto**, independentemente do estado dos gates
individuais.

---

## 5. O que M9.4 NÃO exige

- Não exige renomear gates para letras A–H.
- Não exige alterar thresholds.
- Não exige alterar regras fiscais.
- Não exige criar novos casos no golden dataset, salvo se a
  cobertura de taxonomia ou de regras NUNCA se mostrar incompleta
  em auditoria futura.
- Não exige modificar `runner.py` sem que a etapa (5) da §4
  demonstre uma quebra concreta.

## 6. Próxima evidência (M9.4-D2)

Com este contrato fixado, o próximo ciclo verifica, em ordem:

    dataset_v1.json
          ↓
    carregar_dataset
          ↓
    carregar_schema
          ↓
    avaliar_com_gates  (Gate 0..8)
          ↓
    resultado global
          ↓
    --publicar
          ↓
    snapshot em EVAL_ULTIMA_EXECUCAO_PATH
          ↓
    workflow de CI
          ↓
    GET /api/v1/eval/ultima-execucao

Só haverá código novo se alguma seta estiver quebrada. A auditoria
de D2 deve produzir, no mínimo:

- o nome do workflow de CI que roda o eval (ou a constatação de
  que ele não existe);
- o comando exato executado;
- o path exato do snapshot gerado;
- o resultado do `GET /api/v1/eval/ultima-execucao` após a última
  execução.

## 7. Revisão deste contrato

Este documento pode ser revisado se:

- a definição histórica de A–H for recuperada (improvável), caso
  em que será citada sem substituir a definição operacional;
- o runner mudar de forma que a §3.2 fique desatualizada;
- o CI ou o endpoint mudarem de forma que a §4 precise ser
  reescrita.

Em qualquer revisão, a §2 ("O que NÃO é afirmado aqui")
permanece como regra: nada de inventar correspondência com a
história.
